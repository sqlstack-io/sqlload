---
title: "load"
description: "Load the selected tables of a project, reload them from scratch, follow a Postgres CDC source, and print the result as JSON."
---

```bash
sqlload load [SELECTOR ...] [OPTIONS]
```

`sqlload load` loads the selected tables, creating any that don't exist yet. It prints the
[plan](/docs/cli/plan/) first, then a line per table. It takes the same
[options](/docs/cli/plan/#options) as `plan`.

## Loading

```console
$ sqlload load
…
loaded   raw.app__customers  50 rows  0.0s
loaded   raw.app__orders     1,000 rows  0.0s

✓ Completed  2 loaded, 1,050 rows, 0.1s
```

Each table prints `created`, `altered`, `loaded` or `failed`. A failed table doesn't stop the
others; the summary counts them and the command exits 1, or 75 when every failure may pass on a
rerun (see [Retrying failed runs](/docs/cli/#retrying-failed-runs)).

### Stopping at the first failure

From 0.43.0, `--fail-fast` stops the load once a table fails: no other table starts, and tables
already loading finish and keep what they committed. Each table that never started prints
`skipped` with the table that stopped the run, and the command exits as it would have otherwise: 1,
or 75 when every table that failed, including any still loading when the first failed, may pass on a
rerun. A rerun loads the skipped tables as usual.

```console
$ sqlload load --fail-fast --concurrency 2
…
failed   raw.shop__refunds  GET http://api.example.com/v1/refunds?page=3: HTTP 503: unavailable (after 4 attempts)
loaded   raw.shop__orders   1,200 rows  0.4s
skipped  raw.shop__returns  not started: --fail-fast stopped the load after raw.shop__refunds failed

✗ Completed with failures  1 loaded, 1 failed, 1 skipped, 1,200 rows, 0.5s
```

`--fail-fast` doesn't combine with `--follow`.

Large loads commit along the way, so a failure keeps what committed and the next run carries on from
there; a `delete_insert` into ClickHouse read by cursor publishes once per run instead. See
[Batches](/docs/concepts/cursors/#batches). To read a range instead of continuing from the
destination's maximum, give `--start-cursor` and `--end-cursor`; see [Backfilling a
range](/docs/concepts/cursors/#backfilling-a-range).

## Reloading

`--reload` rebuilds tables from scratch. On a terminal it shows the plan and asks; in scripts, add
`--yes`:

```console
$ sqlload load --reload --yes app__customers
…
loaded   raw.app__customers  50 rows  0.0s

✓ Completed  1 loaded, 50 rows, 0.1s
```

A `postgres_cdc` table is copied again with `--resnapshot` instead; `--reload` refuses it. See
[Reloading](/docs/guides/postgres-cdc/#reloading). `--reload` is also refused on
[Postgres targets](/docs/targets/postgres/).

## Following a Postgres CDC source

`sqlload load SOURCE --follow` keeps streaming one `postgres_cdc` source after it catches up,
writing a batch every `batch_interval`, until `--max-duration` passes or it gets Ctrl-C or
SIGTERM. A second Ctrl-C or SIGTERM stops it at once, with exit code 130. See
[Keep streaming](/docs/guides/postgres-cdc/#keep-streaming).

```bash
sqlload load app --follow --max-duration 10m
```

## Results as JSON

From 0.27.0, `apply --json` and `load --json` print one JSON document on
standard output when they finish, for scripts and orchestrators. Logs stay on standard error. The
exit code is the same as without `--json`.

```console
$ sqlload load --json
{
  "schema_version": 1,
  "command": "load",
  "ok": false,
  "retryable": true,
  "started_at": "2026-11-08T16:33:56.655Z",
  "finished_at": "2026-11-08T16:33:56.731Z",
  "duration_seconds": 0.076,
  "summary": {
    "created": 1,
    "altered": 0,
    "recreated": 0,
    "loaded": 1,
    "failed": 1,
    "skipped": 0,
    "rows": 1200
  },
  "plan": { "ok": true, "summary": "2 selected, 2 objects to create, 2 to load", … },
  "objects": [
    { "action": "created", "name": "raw.shop__orders", "detail": "4 columns" }
  ],
  "tables": [
    {
      "table": "raw.shop__orders",
      "source": "shop",
      "target": "dev",
      "write_strategy": "replace",
      "status": "loaded",
      "rows": 1200,
      "duration_seconds": 0.032,
      "note": null,
      "error": null,
      "retryable": false
    },
    {
      "table": "raw.shop__refunds",
      "source": "shop",
      "target": "dev",
      "write_strategy": "replace",
      "status": "failed",
      "rows": null,
      "duration_seconds": 0.009,
      "note": null,
      "error": "GET http://api.example.com/v1/refunds?page=3: HTTP 503: unavailable (after 4 attempts)",
      "retryable": true
    }
  ]
}
```

| Field | Meaning |
|-------|---------|
| `schema_version` | `1`. New fields can appear without a change; it changes only when a field changes meaning or goes away. |
| `command` | `apply` or `load`. |
| `ok` | Whether every selected table planned and loaded: `true` exactly when the exit code is 0. |
| `retryable` | From 0.34.0. Whether running the command again unchanged may fix every failure: `true` exactly when the exit code is 75. It's `false` when `ok` is `true`, whenever a table failed for good, and whenever a plan error other than an unreachable source left one out. See [Retrying failed runs](/docs/cli/#retrying-failed-runs). |
| `summary` | How many objects were `created`, `altered` (each table once, however many changes it had) and `recreated`; tables `loaded` and `failed`, and from 0.43.0 `skipped`; `rows` loaded. |
| `plan` | The same document `plan --json` prints, with its own `ok` and, from 0.34.0, `retryable`. Tables a plan error left out are in its `errors`, and tables with nothing to load in `skipped`. |
| `objects` | One entry per change to a table or stage, by `apply` or during a load: its `action` (`created`, `altered` or `recreated`), its `name` and the `detail`. A table that gains two columns has two `altered` entries. |
| `tables` | Each table loaded: its `status` (`loaded` or `failed`, or from 0.43.0 `skipped` for a table [`--fail-fast`](#stopping-at-the-first-failure) didn't start, its `error` naming the table that stopped the run and `retryable` `true`), `rows`, `duration_seconds`, a `note` (the cursor window it read, or that its table waits for first data), and the `error` when it failed. From 0.34.0, `retryable` says whether that failure may pass on a rerun. `source`, `target` and `write_strategy` are `null` only for a `load --follow` that failed before any table. From 0.39.0, a files source with `after_load` also has `after_load`: its `action` (`delete` or `move`), `status` (`done`, or `failed` when any file stayed), `files` handled, and `failed`, each file left with its `error`. A table that keeps its files has no such field. `apply` loads nothing, so its list is empty. |

When the run can't start (the configuration doesn't parse, a connection fails), standard output
holds one error document instead, the same as `plan --json`'s:
`{"error": {"code": "config", "message": "…", "help": "…", "retryable": false}}`. `code` is
`config` for the configuration, else the command's name. From 0.34.0,
`retryable` is `true`, and the exit code 75, when the run couldn't start for a reason a rerun may
fix, such as a target that refused the connection or timed out.

`--reload` and `--resnapshot` need `--yes` with `--json`, as there is no prompt to answer.

Under `--json`, what a Python source prints goes to standard error, so standard output holds only
the document. Output written to the process's standard output directly, such as by a child process
that inherits it or `os.write(1, …)`, still reaches standard output: capture or redirect it in the
source.

## Events

From 0.51.0, `--events jsonl` writes each load event to standard error as one line of JSON, next to
the logs, while it happens. `--events-file PATH` writes them to a file instead. Neither combines with
`--follow`. [Prefect and Dagster](/docs/guides/orchestrators/) shows how to send them to an
orchestrator's log.

```console
$ sqlload load --events jsonl 2>&1 >/dev/null
{"schema_version":0,"run_id":"bb60bf2a-…","at":"2026-11-14T17:05:37.263Z","event":"run_started","selected":2,"to_load":2}
{"schema_version":0,"run_id":"bb60bf2a-…","at":"2026-11-14T17:05:37.266Z","table":"raw.items","event":"table_started","strategy":"replace"}
…
{"schema_version":0,"run_id":"bb60bf2a-…","at":"2026-11-14T17:05:37.286Z","table":"raw.items","event":"table_failed","reason":"checks.min_rows failed: 1 row(s) staged, fewer than the 1000 required; nothing was published","retryable":false,"elapsed_ms":18}
{"schema_version":0,"run_id":"bb60bf2a-…","at":"2026-11-14T17:05:37.289Z","table":"raw.orders","event":"table_done","rows":3,"elapsed_ms":22}
{"schema_version":0,"run_id":"bb60bf2a-…","at":"2026-11-14T17:05:37.290Z","event":"run_finished","loaded":1,"failed":1,"not_started":0,"rows":3,"elapsed_ms":62,"exit_code":1}
```

The events are version 0: names and fields can still change in a minor release until
`schema_version` is 1. Every event has `schema_version`, `run_id`, `at` (RFC 3339, UTC) and
`event`, and a table's events have `table`, named as `plan` names it.

| `event` | Fields |
|---------|--------|
| `run_started` | `selected`, `to_load`: the tables selected and the tables the load starts. |
| `table_started` | `strategy`: the write strategy, as `plan` shows it. |
| `table_progress` | `unit` (`page`, `batch`, `window` or `file`), `count` of them read so far, `rows` so far. |
| `rate_limited` | `connection`, its `rate_limit` as `rate`, and `wait_ms`, how long a request waited. No `table`. |
| `table_committing` | `rows`: the table's rows are read and its last commit starts. |
| `table_done` | `rows`, `elapsed_ms`, and `position`, the cursor value it reached, when it keeps one. `changes` lists the `created` and `altered` lines of a table that made or widened its columns while loading. |
| `table_failed` | `reason`, `retryable` (whether a rerun may pass), `elapsed_ms`. |
| `table_not_started` | `reason`, such as the table that stopped a [`--fail-fast`](#stopping-at-the-first-failure) load. |
| `run_finished` | `loaded`, `failed`, `not_started`, `rows`, `elapsed_ms` and `exit_code`. |

On a terminal, `load` also draws a live block of running tables on standard error. The default,
`--progress auto`, leaves it out under `--json` or `--log-format json`; `--progress always` draws it
on a terminal anyway, and `--progress never` leaves it out. Output that isn't a terminal never has
the block or colours.
