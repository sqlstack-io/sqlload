---
title: "plan, apply and load"
description: "Preview a project's changes, create tables, and load data."
---

```bash
sqlload plan  [SELECTOR ...] [OPTIONS]
sqlload apply [SELECTOR ...] [OPTIONS]
sqlload load  [SELECTOR ...] [OPTIONS]
```

| Command | Does |
|---------|------|
| `plan` | Prints what `apply` and `load` would do: tables to create or alter, each column's type mapping, write strategy, route, batches and cursor. Changes nothing. |
| `apply` | Creates or changes destination tables (and Snowflake stages SQLLoad owns). Never loads data. |
| `load` | Loads the selected tables, creating any that don't exist yet. |

`apply` and `load` print the plan first. See [Projects](/docs/concepts/projects/) for how the
three fit together.

## Options

All three take the same options.

| Option | Meaning |
|--------|---------|
| `SELECTOR ...`, `-s`, `--select <SELECTOR>...` | Sources or tables to select: a source name, a destination table name, or a source's `schema.table`. All when none is given. |
| `--exclude <SELECTOR>...` | Sources or tables to leave out. Wins over `--select`. |
| `--start-cursor <VALUE>` | Read from this cursor value instead of the destination's maximum. Typed from each table's cursor: an integer, an RFC 3339 timestamp or a date. |
| `--end-cursor <VALUE>` | Read only cursor values below this one. |
| `--reload` | Rebuild the selected tables from the whole source, with the current columns and types. Asks first, unless `--yes`. Refuses `postgres_cdc` tables, which `--resnapshot` copies again; see [Reloading](/docs/sources/postgres-cdc/#reloading). |
| `--resnapshot` | `postgres_cdc` sources: drop and recreate the replication slot, then copy every table again. Asks first, unless `--yes`. See [Postgres changes](/docs/sources/postgres-cdc/#re-snapshot). |
| `--follow` | `load` of one `postgres_cdc` source only: keep streaming after catching up, writing a batch every `batch_interval`, until `--max-duration` passes or Ctrl-C or SIGTERM. See [Keep streaming](/docs/sources/postgres-cdc/#keep-streaming). |
| `--max-duration <DURATION>` | With `--follow`: stop after this long, such as `10m`, once the changes read so far are written. |
| `--yes` | Rebuild with `--reload` or `--resnapshot` without asking. Needed when not on a terminal. |
| `--allow-type-change-rebuild` | Allow table rebuilds that `type_change_rebuild = "require_confirmation"` would block. |
| `--concurrency <N>` | The most tables loading at once. Default: the project's `concurrency`, else 4. |
| `--json` | Print one JSON document on standard output. For `plan`, the plan. For `apply` and `load` (from 0.27.0), the result: see [Results as JSON](#results-as-json). |

## Reading a plan

```console
$ sqlload plan
Plan ready  2 selected, 2 objects to create, 2 to load

Objects (2)                                         sqlload apply
├── raw.app__customers                              create table
│   ├── customer_id int            -> BIGINT
│   ├── email       text           -> VARCHAR
│   ├── country     text           -> VARCHAR
│   ├── created_at  timestamp_tz   -> TIMESTAMP WITH TIME ZONE
│   └── + _sqlload_load_id, _loaded_at
└── raw.app__orders                                 create table
    ├── order_id    int             -> BIGINT
    ├── customer_id int             -> BIGINT
    ├── status      text            -> VARCHAR
    ├── total       decimal(12,2)   -> DECIMAL(12,2)
    ├── updated_at  timestamp_tz    -> TIMESTAMP WITH TIME ZONE
    └── + _sqlload_load_id, _loaded_at

Loads (2)                                           sqlload load
├── app__customers                                  merge (unique_key: customer_id)
│   ├── source  postgres  app  public.customers
│   ├── route   read as Arrow -> DuckDB takes Arrow
│   └── batch   about every 1 GB
└── app__orders                                     merge (unique_key: order_id)
    ├── source  postgres  app  public.orders
    ├── route   read as Arrow -> DuckDB takes Arrow
    ├── batch   about every 1 GB, in updated_at order (an index leads with it, NULLs first), between distinct values
    └── cursor  updated_at first run, everything

✓ Plan complete  2 selected, 2 objects to create, 2 to load
```

| Section | Lists |
|---------|-------|
| `Objects` | Tables `apply` creates or alters: each column as its portable type `->` the warehouse type, added and widened columns, excluded and masked columns. |
| `Loads` | Each table `load` loads, with its write strategy, and lines for `source`, `files`, `schema`, `route`, `batch`, `cursor`, `state` and `note`. |
| `Skipped` | Tables left out on purpose, such as by `skip_tables_with_columns` or `new_tables = "skip"`, with the reason. |
| `Errors` | Tables that can't load as configured, with the reason and the fix. |
| `Warnings` | Tables that load, but slower or with less than you might expect. |

A table under `Errors` is left out; the others still run, and the command exits 1.

## Loading

```console
$ sqlload load
…
loaded   raw.app__customers  50 rows  0.0s
loaded   raw.app__orders     1,000 rows  0.0s

✓ Completed  2 loaded, 1,050 rows, 0.1s
```

Each table prints `created`, `altered`, `loaded` or `failed`. A failed table doesn't stop the
others; the summary counts them and the command exits 1.

`--reload` rebuilds tables from scratch. On a terminal it shows the plan and asks; in scripts, add
`--yes`:

```console
$ sqlload load --reload --yes app__customers
…
loaded   raw.app__customers  50 rows  0.0s

✓ Completed  1 loaded, 50 rows, 0.1s
```

## Results as JSON

From 0.27.0, `apply --json` and `load --json` print one JSON document on
standard output when they finish, for scripts and orchestrators. Logs stay on standard error. The
exit code is the same as without `--json`.

```console
$ sqlload load --json
{
  "schema_version": 1,
  "command": "load",
  "ok": false,
  "started_at": "2026-11-08T16:33:56.655Z",
  "finished_at": "2026-11-08T16:33:56.731Z",
  "duration_seconds": 0.076,
  "summary": {
    "created": 1,
    "altered": 0,
    "recreated": 0,
    "loaded": 1,
    "failed": 1,
    "rows": 1200
  },
  "plan": { "ok": true, "summary": "2 selected, 2 objects to create, 2 to load", … },
  "objects": [
    { "action": "created", "name": "raw.shop__orders", "detail": "4 columns" }
  ],
  "tables": [
    {
      "table": "raw.shop__orders",
      "source": "shop",
      "target": "dev",
      "write_strategy": "replace",
      "status": "loaded",
      "rows": 1200,
      "duration_seconds": 0.032,
      "note": null,
      "error": null
    },
    {
      "table": "raw.shop__refunds",
      "source": "shop",
      "target": "dev",
      "write_strategy": "replace",
      "status": "failed",
      "rows": null,
      "duration_seconds": 0.009,
      "note": null,
      "error": "RuntimeError: the API returned 503 (File \"/srv/project/sources/shop.py\", line 14, in refunds)"
    }
  ]
}
```

| Field | Meaning |
|-------|---------|
| `schema_version` | `1`. New fields can appear without a change; it changes only when a field changes meaning or goes away. |
| `command` | `apply` or `load`. |
| `ok` | Whether every selected table planned and loaded: `true` exactly when the exit code is 0. |
| `summary` | How many objects were `created`, `altered` (each table once, however many changes it had) and `recreated`; tables `loaded` and `failed`; `rows` loaded. |
| `plan` | The same document `plan --json` prints. Tables a plan error left out are in its `errors`, and tables with nothing to load in `skipped`. |
| `objects` | One entry per change to a table or stage, by `apply` or during a load: its `action` (`created`, `altered` or `recreated`), its `name` and the `detail`. A table that gains two columns has two `altered` entries. |
| `tables` | Each table loaded: its `status` (`loaded` or `failed`), `rows`, `duration_seconds`, a `note` (the cursor window it read, or that its table waits for first data), and the `error` when it failed. `source`, `target` and `write_strategy` are `null` only for a `load --follow` that failed before any table. `apply` loads nothing, so its list is empty. |

When the run can't start (the configuration doesn't parse, a connection fails), standard output
holds one error document instead, the same as `plan --json`'s:
`{"error": {"code": "config", "message": "…", "help": "…"}}`. `code` is `config` for the
configuration, else the command's name.

`--reload` and `--resnapshot` need `--yes` with `--json`, as there is no prompt to answer.

Under `--json`, what a Python source prints goes to standard error, so standard output holds only
the document. Output written to the process's standard output directly, such as by a child process
that inherits it or `os.write(1, …)`, still reaches standard output: capture or redirect it in the
source.
