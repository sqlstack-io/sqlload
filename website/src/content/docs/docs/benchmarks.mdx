SQLLoad, dlt and ingestr loaded the same data on the same machine, one after another, with every
run's result checked against the source. These are the published scenarios, all from the
repository's [benchmarks README](https://github.com/sqlstack-io/sqlload/blob/main/benchmarks/README.md),
which also has peak memory for every run and the commands to reproduce them.

| Scenario | SQLLoad | Next fastest | SQLLoad's lead |
|----------|---------|--------------|----------------|
| Parquet folder into DuckDB, 10M rows | 3.20&nbsp;s | ingestr 5.85&nbsp;s | 1.83x |
| Parquet folder into DuckDB, 1M rows | 0.92&nbsp;s | ingestr 2.12&nbsp;s | 2.32x |
| Parquet in S3 into DuckDB, 10M rows | 8.92&nbsp;s | ingestr 10.01&nbsp;s | 1.12x |
| Postgres, 40 columns, into DuckDB, 1M rows | 6.84&nbsp;s | ingestr 8.29&nbsp;s | 1.21x |
| The same table without a primary key | 6.75&nbsp;s | ingestr 8.75&nbsp;s | 1.30x |
| Postgres into Snowflake, 1M rows | 14.56&nbsp;s | ingestr 16.38&nbsp;s | 1.12x |
| Postgres, 40 columns, into Snowflake, 100,000 rows (external stage) | 11.60&nbsp;s | ingestr 14.42&nbsp;s | 1.24x |
| The same table without a primary key (external stage) | 12.25&nbsp;s | ingestr 14.61&nbsp;s | 1.19x |
| Parquet in S3 into Snowflake, 1M rows | 10.30&nbsp;s | ingestr 19.47&nbsp;s | 1.89x |

Wall time is the median of 5 runs. dlt was slower than both in every scenario it ran.

## Basis

- **Date:** 6 November 2026.
- **Hardware:** a shared cloud VM with 4 vCPUs (Intel Xeon @ 2.60 GHz) and 8 GB of RAM, Linux 6.1.
- **Versions:** dlt 1.32.0 (writing with DuckDB 1.5.6), ingestr 1.1.82, Postgres `postgres:17`,
  Python 3.12.14. SQLLoad is the release wheel built from commit `07a6510` (released as 0.11.0) or
  `5ab2b9e` (0.11.1), as each table names.
- **Method:** one warm-up, then the median of 5 runs, rotating which loader starts each round. Each
  run gets a fresh destination, `HOME` and XDG folders. Wall time, and user plus system CPU of the
  loader's process tree. Every run's row count and checksum matched the source. No loader is tuned.
- **Data:** seed 42. Narrow rows have 6 columns; the wide table has 40, including 2 `jsonb`. Parquet
  scenarios load the narrow rows as 10 part files.
- **S3:** the bucket was in eu-west-2 and the machine in us-west-2, so every request crossed
  regions.
- **Snowflake:** an X-Small warehouse in AWS eu-west-2. Wall time includes Snowflake's own `COPY`.

## Into Snowflake

`sqlload (external stage)` stages them in S3; `sqlload (direct)` lets Snowflake read the Parquet

## Running them yourself

The suite needs Docker, uv and the Rust toolchain, and runs from a clone of the repository:

```bash
make bench-compare BENCH_ARGS='--size reduced'
```

The [benchmarks README](https://github.com/sqlstack-io/sqlload/blob/main/benchmarks/README.md)
lists every scenario, the Snowflake settings, and what each run touches.
