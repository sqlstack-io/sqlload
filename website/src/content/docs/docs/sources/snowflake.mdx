From sqlload 0.26.0, a Snowflake source loads tables and views of one
database, and the results of queries you write.
Snowflake unloads each read as Parquet with `COPY INTO`, and SQLLoad reads the files and loads
them into the source's target. From 0.27.0 (not released yet), a DuckDB target reads them from S3
itself.

```toml
[connections.warehouse]
kind = "snowflake"
account = "myorg-myaccount"
user = "loader"
auth = { method = "pat", token = "${ENV:SNOWFLAKE_TOKEN}" }
warehouse = "LOAD_WH"
database = "ANALYTICS"

[sources.shop]
kind = "snowflake"
connection = "warehouse"
description = "Order tables of the shop's warehouse."
include = ["SHOP.ORDERS"]

[sources.shop.tables."SHOP.ORDERS"]
description = "Orders, one row per order."
cursor_column = "order_date"
write_strategy = "delete_insert"
lookback = "7d"
lookahead = "7d"
lookback_from = "now"

[sources.shop.tables.big_orders]
description = "Orders of 500 or more."
sql = "SELECT ORDER_ID, CUSTOMER_ID, PLACED_AT, TOTAL FROM SHOP.ORDERS WHERE TOTAL >= 500"
```

A connection that only a source reads needs no `load_method`. Set one when a target loads into
the same connection.

```console
$ sqlload plan
```

## Choosing tables

`include` and `exclude` are `SCHEMA.TABLE` patterns of the connection's database, matched without
regard to case (`*` matches any text). Views match too. A `[sources.shop.tables."SCHEMA.TABLE"]`
entry sets options for one table; on its own, it doesn't add the table. Write its key as Snowflake
stores the name, normally in upper case.

A source needs at least one `include` pattern or one query table.

Snowflake stores unquoted names in upper case. A column such as `ORDER_ID` loads as `order_id`.
A name created in quotes with other characters, such as `"OrderId"`, loads exactly as written.

## Query tables

A table entry with `sql` is a query table: its rows are the query's result, and the entry's key is
its name. SQLLoad reads the query's columns at `plan` without reading any rows.

`cursor_column` names a column of the query's result. SQLLoad wraps the query and filters on the
cursor outside it, so the query itself needs no placeholder.

## Read windows

A table with a `cursor_column` reads from the destination's maximum, less any `lookback`. Two
settings move the window to the time of the run instead:

| Setting | Effect |
|---------|--------|
| `lookback_from = "now"` | Start `lookback` before now, not before the destination's maximum. Needs a `lookback`. |
| `lookahead` | Read only cursor values before now plus this. A date cursor reads up to and including today plus that many days. |

`lookback = "7d"`, `lookahead = "7d"` and `lookback_from = "now"` read from 7 days ago to 7 days
ahead on every run, which suits tables whose rows change for a while and include future dates.
Use `write_strategy = "delete_insert"` with them, so each run replaces the whole window.

Days are counted in UTC. The first run reads the same window. `--start-cursor` and `--end-cursor`
override it for one run. `--reload` rebuilds the table from `cursor_start`, or from the first row,
up to the lookahead. A files target takes neither setting: its window follows its newest
partition.

## Where the files go

| `stage` | Snowflake writes to | SQLLoad reads with |
|---------|---------------------|--------------------|
| Omitted | A folder of your user stage, `@~/sqlload_unload/` | The temporary credentials Snowflake hands out, several files at a time |
| `{ url = "s3://example-bucket/unload/", storage_integration = "S3_UNLOAD", region = "eu-west-2" }` | That S3 folder, through the storage integration | Its AWS credentials, found as for an [`s3` connection](/docs/configuration/#s3) (the shared credentials file from 0.27.0, not released yet) |
| `{ name = "ANALYTICS.SHOP.UNLOAD_STAGE" }` | That stage, internal or external on S3 | As for the rows above |

The user stage and other internal stages work on Snowflake accounts hosted on AWS. A named internal
stage must use Snowflake's default client-side encryption; one created with
`ENCRYPTION = (TYPE = 'SNOWFLAKE_SSE')` is refused when the table loads.

Each read unloads into a folder of its own, which SQLLoad removes after the read, when the read
fails too. A read fails when the files hold a different number of rows than `COPY INTO` reports.
A run that is killed can leave its folder behind; remove such folders with `REMOVE`, or with a
lifecycle rule on the bucket.

With an external stage, SQLLoad needs to list, read and delete objects under the folder. The
storage integration must allow Snowflake to write there.

### DuckDB reads the files itself

From 0.27.0 (not released yet). With a stage given by `url` and a DuckDB target, DuckDB reads the unloaded files from S3 itself,
so no rows pass through SQLLoad. `plan` shows it in the route:

```text
route   unload Parquet to s3://example-bucket/unload/ -> DuckDB reads them (nothing through the loader)
```

DuckDB uses the same S3 credentials as SQLLoad, and turns times and timestamps back exactly,
whatever its session time zone. A load fails before it commits when DuckDB loads a different number
of rows than `COPY INTO` reports, and the folder is removed either way. A table without a cursor
commits once per run rather than about every 1 GB.

Without a stage, from 0.27.0 (not released yet), SQLLoad downloads the files from the user stage
unchanged, 16 at a time, into a temporary folder, and DuckDB reads them from there:

```text
route   unload Parquet to internal stage @~/sqlload_unload/ -> download unchanged to a local temporary folder -> DuckDB reads them (nothing through the loader)
```

The folder, named `sqlload-unload-…`, is in the system's temporary directory (`TMPDIR`). It needs
room for one read's files (the whole table, or one window with `batch_size`) for each table loading
at once, up to `concurrency`. Where the temporary directory is in memory (tmpfs), so are the files.
The folder is removed after the read, when the read fails too; a run that is killed can leave it
behind.

SQLLoad reads the files instead, and `plan` says why, for a table with masked columns or checks
before publish, for a stage given by `name`, and for targets other than DuckDB.

## Permissions

The role needs `USAGE` on the warehouse, database and schemas, and `SELECT` on the tables and
views. An external stage given by `url` also needs `USAGE` on the storage integration; one given by
`name` needs `USAGE` on the stage, or `READ` and `WRITE` on an internal one.

## Types

| Snowflake | Loads as |
|-----------|----------|
| `NUMBER(p,0)`, p up to 18 | `int` |
| `NUMBER(p,s)` otherwise, including `INTEGER` (`NUMBER(38,0)`) | `decimal(p,s)` |
| `FLOAT` | `float` |
| `VARCHAR(n)`; default length | `varchar(n)`; `text` |
| `BOOLEAN`, `DATE`, `TIME`, `BINARY` | `bool`, `date`, `time`, `binary` |
| `TIMESTAMP_NTZ` | `timestamp_ntz` |
| `TIMESTAMP_TZ`, `TIMESTAMP_LTZ` | `timestamp_tz`, the instant in UTC |
| `VARIANT`, `OBJECT`, `ARRAY` | `json` |

Times and timestamps keep their microseconds. Other types, such as `GEOGRAPHY`, need a pinned type,
such as `columns = { area = "text" }`. Pin `int` on an `INTEGER` column whose values fit 64 bits,
such as `columns = { order_id = "int" }`. See [Types](/docs/types/).
