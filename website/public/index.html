Where loads go wrong

Hidden state drifts from reality

A stored copy of the schema or the cursor disagrees with the warehouse, and the fix is deleting state you can't see.

Types quietly change

Decimals lose digits, JSON turns into strings, a column that's all NULL never gets created, and a stray value becomes a second column.

Big tables take the server down

A large first load buffers everything in memory, and the run dies with no report.

Nothing says no

No step shows what a run will change, or stops when something's wrong.

Plan, apply, load

One sqlload.toml, three commands, and nothing kept outside your warehouse.

02 · Load

Bulk copy, not row inserts

Files in S3 load into Snowflake straight from an external stage, and Parquet in S3 into Databricks through an external location. Parquet loads into DuckDB through DuckDB's own reader, and Parquet in S3 into MotherDuck on its servers. Snowflake tables load into Snowflake on the same connection, or through an external stage that covers the unload, without leaving Snowflake. Rows are staged as Parquet and copied in bulk.

04 · Keep types exact

Declare what matters

05 · Write sources in Python

APIs without the plumbing

Yield dicts, Arrow data or JSON bytes. HTTP pagination, fan-out, retries and rate limits run in Rust.

Python sources →

import sqlload as sl

shop = sl.source("shop", connection="shop")
api = sl.http(shop, auth=sl.bearer(), rate_limit="10/s")

@shop.table(unique_key="order_id")
def orders(ctx):
    """Orders, one row per order."""
    return api.paginate("/orders", select="$.items",
                        paginator=sl.page_number("page"))
